รายงานนี้บันทึกกระบวนการพัฒนาและเสริมความทนทาน ไม่ใช่ประกาศออกเวอร์ชัน สแนปช็อตเครื่องเล่นที่วัดคือ `652726f8` ส่วนสแนปช็อต Android เนทีฟที่สร้างแยกคือ `be0d800` CI การผสาน และการเลื่อนขั้นรุ่นยังเป็นด่านแยกกัน คอมมิตภายหลังที่เปลี่ยนเฉพาะเอกสารหรือการทดสอบไม่ได้ทำให้การตรวจในเครื่องกลายเป็นหลักฐานว่าอุปกรณ์ที่ติดตั้งได้รับการอัปเดตแล้ว สถานะด่านด้านล่างเป็นของสแนปช็อตในอดีตเหล่านั้น ไม่ใช่ตัวติดตามรุ่นแบบสด ดูบิลด์ที่เผยแพร่แล้วได้ที่ [GitHub Releases](https://github.com/open-ott-play/ottplay-foss/releases)

## ตรวจสอบงานอย่างไร

คำขอเริ่มต้นถูกแบ่งเป็นฟีเจอร์ที่ใช้งานได้ 13 ส่วนในเครื่องเล่นคลาสสิก บริการควบคุม/CLI และแอป Android เนทีฟอิสระ มอบหมายผู้รับผิดชอบตามองค์ประกอบเพื่อให้ตรวจทานและรวมการเปลี่ยนพร้อมกันได้โดยไม่ทับงานองค์ประกอบอื่น UI ใหม่ใช้ป้ายที่แปลไว้แล้วหรือเพิ่มรายการแค็ตตาล็อกครบ 88 ภาษา คู่มือวิศวกรรมฉบับเต็มเดิมเขียนเป็นภาษาอังกฤษและรัสเซีย ปัจจุบันคู่มือหลักและคู่มือฟีเจอร์ที่จับคู่มีฉบับเต็มใน [24 ภาษาเอกสาร](manual-translations.md)

หลังพัฒนามีการตรวจทานข้ามอย่างอิสระและการทดสอบการถดถอยที่รันได้ ปัญหาที่รายงานถูกตรวจเทียบกับเส้นทางคอลแบ็ก ตัวถอดรหัส ที่เก็บ หรือโฟกัสจริงก่อนเปลี่ยนโค้ด ความล้มเหลวการทดสอบถูกแยกเป็นการถดถอยของพฤติกรรมกับตัวเลือกทดสอบที่ล้าสมัย เช่น การเปลี่ยนแถวคลาสสิกจาก `button` เป็น `option` ต้องอัปเดตตัวเลือก แต่ไม่ใช่เหตุผลให้ลดข้อกำหนดพฤติกรรมคลิกที่คาดหวัง

จากนั้นบิลด์โปรดักชันสะอาดตรวจผลลัพธ์ ES5 และต้นทุน JavaScript ทั้งหมด รวมโมดูลผู้ให้บริการเสริม การทดสอบเบราว์เซอร์เฉพาะจุดใช้ตัวโหลด บันเดิล และอะแดปเตอร์อุปกรณ์ที่จัดส่งจริง Android เนทีฟมีการรัน Gradle test, lint และสร้างแพ็กเกจแยกกัน หลังพุชต้องตรวจ PR checks และกระทู้รีวิวอีกครั้ง บิลด์ในเครื่องที่ผ่านไม่ใช่สิ่งทดแทน

## สิ่งที่เปลี่ยนระหว่างรีวิว

![พฤติกรรมที่แก้ห้ารายการและต้นทุน JavaScript ที่วัด](diagrams/implementation-results.svg)

- **การแยกวิเคราะห์ HLS และลองซ้ำ:** เดิมข้อผิดพลาดการแยกวิเคราะห์อยู่ในหมวดเครือข่ายทั่วไป ตอนนี้ให้เชื่อมต่อ URL เดิมใหม่ได้สูงสุดหนึ่งครั้งภายในโควตาสองครั้งของข้อผิดพลาดชั่วคราว ตัวถอดรหัสและ URL สำรองใหม่ไม่รีเซ็ตโควตา ข้อผิดพลาดยืนยันตัวตน/DRM ขั้นสุดท้ายยังยกเลิกการลองชั่วคราวที่เข้าคิวแล้วด้วย
- **ทางเลือกเนทีฟ Auto:** การจัดการข้อผิดพลาดเนทีฟอาจเลิกคำขอทั้งที่ Auto เป็นเจ้าของการเปลี่ยนไปทางเลือกแล้ว ตอนนี้เจ้าของเดิมรักษาการเปลี่ยนนั้นไว้ การยกเลิกยังทำให้คอลแบ็กที่หน่วงไว้ใช้ไม่ได้
- **Enter ในโมดัล:** การโฟกัสปุ่มยกเลิกแรกอัตโนมัติทำให้ Enter ในกล่องรอ Plex กลายเป็นยกเลิก ตอนนี้กล่องเริ่มโดยโฟกัสที่ตัวกล่องเอง Tab จะเข้าถึงปุ่มอย่างชัดเจน กล่องข้อมูลและยืนยันปกติคงพฤติกรรม Enter และ Escape/ย้อนกลับ
- **การเลือกด้วยตัวชี้บน PC:** โฟกัสเมาส์เปลี่ยนรายการเลือกก่อนตัวจัดการคลิก ทำให้คลิกแรกเป็นการเปิดใช้งาน โฟกัสจากตัวชี้จะไม่เลือกแถวล่วงหน้าอีก PC ยังเลือกก่อนแล้วค่อยเปิดใช้งาน ส่วน LG คงการคลิกครั้งเดียว โฟกัสแป้นพิมพ์ยังตามรายการเลือก
- **แทร็ก Android:** การเลือกที่ไม่มีป้ายของรายการปัจจุบันอาจถูกลบโดยการยืนยัน Auto ของตัวเองหรือการอัปเดตค่าคำบรรยาย หรือรั่วไปอีกรายการที่มี `TrackGroup` เท่ากัน ตอนนี้การเลือกจะอยู่รอดจากการเขียนล่าช้าเฉพาะรายการปัจจุบัน ค่าที่มีความหมายใช้ภาษา/บทบาท/ป้าย โดย ViewModel เป็นเจ้าของการบันทึกถาวร การปิดแผงจึงไม่ยกเลิกการเขียน

ฟีเจอร์ที่ส่งมอบ 13 ส่วนคือ ตัวอย่าง A/V; การตั้งค่า Local/Home ที่ทำต่อได้; การกู้คืนแบบจำกัด; เพดานคุณภาพ; ค่าแทร็ก Android; คีย์ควบคุมจำกัดขอบเขต; การผูก XMLTV; ภาพยนตร์/ซีรีส์ Xtream; การช่วยการเข้าถึงคลาสสิก; ผลคำสั่งที่คงทน; การส่งต่อชัดเจน; สตรีมสำรอง; และชุดการตั้งค่าที่กู้คืนได้ [คู่มือฟีเจอร์](roadmap-delivery.th.md) กำหนดขอบเขตและข้อจำกัดแต่ละส่วน

## หลักฐานและด่านที่ยังเหลือ

สำหรับ `652726f8` สถานการณ์เบราว์เซอร์เฉพาะจุดทั้งห้าผ่าน ได้แก่ การนำทางตัวชี้ LG webOS, LG NetCast, พฤติกรรมสองคลิกบน PC, ความหมายแป้นพิมพ์ในกล่องโต้ตอบ และ Plex คอลเลกชัน/แก้การอ้างอิง/ยกเลิก/ลองใหม่ TypeScript, ชุดทดสอบหน่วยการช่วยการเข้าถึง, lint จำกัดขอบเขต, ES5 และงบขนาดบันเดิลผ่าน การรันเบราว์เซอร์เต็มบนบิลด์นี้จบด้วย **ผ่าน 194 และข้ามหนึ่ง** เพราะ HLS เนทีฟต้องใช้ WebKit แต่รอบนี้ใช้ Chromium CI ที่โฮสต์และลำดับผสานที่ตกลงกันยังเป็นด่านแยก

สาย `test:port` และ `test:unified` ที่เหลือเสร็จผ่านการรันต่อเป็นช่วงหลังแก้ชุดเตรียมทดสอบเฉพาะจุด เป้าหมายที่เคยล้มเหลวทุกรายการถูกรันซ้ำสำเร็จ และคำสั่งที่เหลือจบสำเร็จ นี่ไม่ใช่การอ้างว่ารัน `npm test` ครั้งเดียวต่อเนื่อง ขั้น CI ของบริดจ์ Android ที่มีเก้าคำสั่งตรงตามจริงก็ผ่านในเครื่อง

สำหรับ Android `be0d800` **การทดสอบแอป 101 รายการและแกนร่วม 62 รายการ** ผ่านในเครื่อง รวมถึง lint debug/release, การสร้าง APK Debug/Release/Full, บันเดิลรีลีส และการคอมไพล์ APK androidTest การคอมไพล์ APK ทดสอบแบบ instrumented ไม่ใช่การรันบนอุปกรณ์ ข้อค้นพบรีวิวที่ยืนยันแล้วสามรายการได้รับคำตอบและแก้ใน [Android PR 68](https://github.com/open-ott-play/ottplay-android/pull/68) PR นั้นผ่านการตรวจและผสานเป็น `5b644b94` ส่วน CI หลังผสานติดตามแยก แผนภาพยังแสดงด่าน CI/รีลีสรวมของเครื่องเล่นว่ารอดำเนินการ

JavaScript เว็บทั้งหมดเปลี่ยนจาก **964,459 / 305,344** ไบต์ raw/gzip เป็น **995,858 / 315,207**: **+31,399 / +9,863 ไบต์** (ประมาณ 3.26% / 3.23%) รุ่นผู้สมัครฟีเจอร์มี 995,587 / 315,103 การเสริมความทนทานภายหลังเพิ่ม 271 / 104 จุดเข้าหลักสุดท้ายของสแนปช็อตนั้นคือ 875,197 / 270,425 ดู [การวัดฐาน](evidence/roadmap-size-20261015.json), [การวัดผลลัพธ์สุดท้าย](evidence/roadmap-final-size-20261015.json) และ [วิธีวัด](roadmap-size.th.md)

นี่คือต้นทุนไบต์ JavaScript ในอดีต **ไม่ใช่ความเร็วที่เพิ่มขึ้นซึ่งวัดแล้ว** ยอดรวมไม่รวมเอนจินสื่อ พจนานุกรม CSS รูปภาพ และวิดีโอ แพ็กเกจของสแนปช็อตนั้นมีคลิป A/V 464,652 ไบต์แยกต่างหาก หลัง [เปลี่ยนโฮสติ้ง](audio-video-check.th.md) ไฟล์ `diagnostics/av-v1.mp4` ยังอยู่ในรีโพพร้อมตัวสร้างและตัวตรวจเพื่อให้ทำซ้ำได้ แต่ไม่รวมในแพ็กเกจ Web/OTTPlay Server, Tauri, Capacitor และ Docker เครื่องเล่นดึงจาก here.now เฉพาะการตรวจ A/V ที่ผู้ใช้สั่งซึ่งต้องมีอินเทอร์เน็ต การเล่นตอนเริ่มต้นไม่ดึงไฟล์ การลบสื่อดิบ 464,652 ไบต์ไม่ได้ระบุขนาดที่ประหยัดในตัวติดตั้งบีบอัดหรือเปลี่ยนค่าที่วัด JavaScript ในอดีต เวลาเริ่มต้น ความสม่ำเสมอเฟรม หน่วยความจำ ประสบการณ์โปรแกรมอ่านหน้าจอ เสียง HDMI จริง และพฤติกรรมผู้ให้บริการต้องวัดแยกบนอุปกรณ์เป้าหมาย รายงานนี้ไม่อ้างผลบนอุปกรณ์จริงใหม่หรือการออกเบตา [รายการตรวจรับอุปกรณ์จริง](roadmap-delivery.th.md#physical-acceptance-before-promotion) และ [กลยุทธ์รีลีส](../RELEASING.md) ยังเป็นเกณฑ์เลื่อนขั้น

## การรวมและรีวิวหลังเบตา

หลังเผยแพร่ beta.4 ได้รวมซอร์ส `39287792` ในสาขานี้ รีวิชันรันไทม์ `9663b681` ยังแก้การกลับไปขอบสดภายใต้เพดานคุณภาพ HLS และทำให้กู้คืนวารสารการตั้งค่าที่เสียหายก่อนเริ่มปกติได้ หน้าจอกู้คืนกันการโหลดสถานะบัญชีเพียงบางส่วน รองรับลองใหม่และรีเซ็ตแบบยืนยัน รักษาคุกกี้ที่ไม่เกี่ยวข้อง และป้องกันการตั้งค่าคุกกี้เก่ากลับมาหลังรีเซ็ต ดู [กระบวนการกู้คืน](settings-recovery.th.md) และแผนภาพ SVG

![เปรียบเทียบ JavaScript ทั้งหมดหลังเบตา](diagrams/post-beta-size.svg)

การสร้างซ้ำจากทั้งสองซอร์สด้วย Node 26.8.2, Rollup 4.64.5 และ Terser 5.51.2 ให้ **964,876 / 305,452** ไบต์ raw/gzip สำหรับซอร์ส beta.4 และ **1,000,388 / 316,600** สำหรับรุ่นรวม: **+35,512 / +11,148 ไบต์** (3.68% / 3.65%) รวมผู้ให้บริการเสริมทั้งหมด เจ็ดรายในฐานและแปดรายในรุ่นรวม จุดเข้าใหม่คือ 879,533 / 271,761 เป็นการเปรียบเทียบคนละชุดกับกราฟเก่าที่ตรึงไว้ข้างต้น

บิลด์โปรดักชันในเครื่องทั้งสองสร้างไฟล์รันไทม์ที่ติดตามอยู่ห้าไฟล์ใหม่และไม่กล่าวอ้างรีวิชันซอร์สสะอาด รายงานบันทึกข้อจำกัดนี้แทนการระบุไฟล์ในเครื่องเป็นผลลัพธ์รีลีสที่เผยแพร่แล้ว: [ฐาน](evidence/post-beta-baseline-size-20261015.json) และ [รุ่นรวม](evidence/post-beta-candidate-size-20261015.json) บิลด์รวมและการตรวจ ES5/เนทีฟผ่าน การตรวจเบราว์เซอร์เฉพาะจุดหกอย่างก็ผ่าน ได้แก่ กู้คืน/รีเซ็ตวารสาร แป้นพิมพ์กล่องโต้ตอบ ตัวชี้ LG webOS และ NetCast การเลือกสองคลิก PC และการรอ Plex ที่มีเจ้าของ

## การรวมด่านเบราว์เซอร์

![ผลตรวจเบราว์เซอร์ในเครื่องที่ยืนยันแล้ว](diagrams/browser-verification-results.svg)

ซอร์ส `c52f4d07` รวม PR 779 จาก main `1ecbc0e7` คงคำสั่งทดสอบ การตรวจกู้คืน และข้อยืนยันกล่อง Plex ของทั้งสองสาขา TypeScript, lint, เอกสาร, ข้อตกลงแพ็กเกจ/ลิงเกอร์, บิลด์โปรดักชัน และการตรวจบันเดิลที่คอมไพล์ทั้งหมดผ่าน ไฟล์ JavaScript เครื่องเล่น/ผู้ให้บริการที่สร้างทั้ง 27 ไฟล์ยังเหมือนผลลัพธ์ที่วัดข้างต้นทุกไบต์ ชุดทดสอบอุปกรณ์-เบราว์เซอร์เต็มบนบิลด์นี้จบด้วย **ผ่าน 196 และข้าม Chromium หนึ่งรายการตามคาด** สำหรับ HLS เนทีฟที่ต้องใช้ WebKit

อาร์ไคฟ์ Mode A ที่แพ็กจริงถูกแตกหลังตรวจซอร์ส เช็กซัม และรายการบันเดิล/ผู้ให้บริการแล้วเท่านั้น Chromium 156.0.8078.4, Firefox 157.0 และ WebKit 27.2 ต่างผ่านสถานการณ์โปรไฟล์ทั้งห้าโดยไม่ข้ามหรือรันซ้ำ: **ผ่านในเครื่อง 15 รายการ** ด้วย Playwright 1.64.0 โฮสต์จริงคือ macOS 26.7.1 ไม่ใช่รันเนอร์ `macos-15` ที่ระบุในโปรไฟล์ที่เลือก บันทึกหลักฐานระบุความต่างนี้ชัดเจน และ **ไม่ใช่การรับรองเมทริกซ์ที่โฮสต์หรือคุณสมบัติรีลีส** ดู [สรุปในเครื่อง](evidence/post779-local-acceptance/summary.json) และ [วิธีทำซ้ำ](evidence/post779-local-acceptance/reproduce.sh) ซึ่งต้องมีบิลด์โปรดักชันอยู่แล้วและปฏิเสธการแทนที่ไดเรกทอรีรุ่นผู้สมัครที่แตกไว้

[นโยบายเบราว์เซอร์](browser-compatibility.th.md) กำหนดห้าเป้าหมายที่โฮสต์และ 25 การรันสถานการณ์สำหรับ PR/เบตา ส่วน RC เต็มมี 35 เป้าหมายและ 166 การรัน นี่คือข้อกำหนดที่ตั้งไว้ ไม่ใช่ความครอบคลุมที่วัดแล้ว

![การตรวจรุ่นผู้สมัครสร้างหลักฐานอย่างไร](diagrams/candidate-verification-flow.svg)

[ไปป์ไลน์เบตา](https://github.com/open-ott-play/ottplay-foss/actions/runs/38856793467) แยกของ main `1ecbc0e7` เสร็จสำเร็จ แต่ไม่มี PR นี้ รุ่นรวมยังต้องผ่าน CI ที่โฮสต์และรีวิวของตน แล้วจึงประสานงานรีลีส ผลในเครื่องข้างต้นไม่ได้อ้างว่าผ่านด่านส่งมอบเหล่านี้แล้ว
