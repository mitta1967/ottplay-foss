בדיקות המכשירים, המדיה, ES5/workers הישנים, הממשק המקורי ו־HLS המקורי של Apple נותרות חובה. תהליך העבודה המשותף של TypeScript מריץ גם תרחישי Plex מול אותו ארכיון Mode A ארוז בדיוק: שני מסלולי טעינה/טעינה מחדש מתורגמים, שמירת יחס התמונה ב־HLS.js וב־Video.js בעת החלפת מדיה או טעינה מחדש, וסיום טבעי של פרק בקיוסק המחמיר עם HLS.js. תרחישי המדיה משתמשים בפענוח אמיתי; כל התרחישים משתמשים ב־DOM ובקלט אמיתיים. רק נתוני Plex ומקור המדיה הם נתוני בדיקה מקומיים סינתטיים.

דגימת יחס התמונה אורזת מחדש את זרם התעבורה H.264/AAC השמור במאגר לגרסאות fMP4 נפרדות. כותרות האתחול משתמשות במותג `iso6` ובמשך סרט/רצועה אפס כנדרש ב[סעיף 3.3 של RFC 8216](https://www.rfc-editor.org/rfc/rfc8216#section-3.3). רשומת דגימת AVC משתמשת גם בסיביות השמורות הנדרשות במניין SPS ובקבוע בעל הסימן `-1` בשדה המסיים `pre_defined`. כך מתוקן תחביר המכולה שמפיק המרבב הנעול של נתוני הבדיקה. חוזה הדגימה בודק את הכותרות ודוחה תיבות פגומות, תוך הוכחה שקבוצות פרמטרי המקודד, מזהי הרצועות, סולמות הזמן ובתי מקטעי המדיה לא השתנו. זה מאמת את הקלט הסינתטי; לבדו אינו מוכיח ניגון בדפדפן ואינו מחליף את מטריצת RC המלאה.

בקשות משיכה מחייבות Chromium, Firefox ו־WebKit עדכניים ב־Linux, את Chromium ב־Windows ואת WebKit ב־macOS. בניות לילה ו־beta מחייבות אותם חמישה יעדים. הסמכת RC מחייבת את כל 35 היעדים המוצהרים: שלושה דורות מדויקים של Playwright/דפדפנים ב־Linux, Windows ו־macOS, וכן Chrome/Edge יציבים מותקנים בשלוש המערכות ו־Chrome/Edge beta ב־Linux. שני יעדי macOS WebKit ההיסטוריים (Playwright 1.62.1 ו־1.63.0) משתמשים ב־`macos-15-intel`; אסמכתאותיהם מתעדות את ארכיטקטורת התהליך בפועל ודוחות ראנר ARM. אבחון MSE ישיר מצא שאותם בתי אתחול H.264 ומדיה הושלמו ב־Intel עם 1.63 וב־ARM עם 1.64, ואילו WebKit ישן במכונת macOS 15 ARM הווירטואלית נתקע לפני `updateend`. החלפת מכולות, שימוש ב־ManagedMediaSource או פתיחת חלון דפדפן לא פתרו זאת. שני היעדים עדיין מחייבים את כל חמשת תרחישי הניגון/ממשק המקוריים. בחירת הראנר אינה טענה על כל מכשיר macOS פיזי או על Safari המקורי. יצירה מחדש של המצאי חייבת לשמר את דריסות הראנר שנבדקו; חוזה הפרופיל דוחה את הסרתן.

כל שלושת דורות Linux WebKit משתמשים במפורש בראנר x64 `ubuntu-26.04`. ההשוואה שנבדקה בין סביבות הריצה הרשמיות שחזרה כשל במעבר הקיוסק המחמיר ב־Ubuntu 24.04, ואילו אותו מועמד וחמישה תרחישים ללא שינוי עברו ארבע פעמים רצופות ב־Ubuntu 26.04. כך נבחרת סביבת ריצה עקבית ונתמכת בלי החלפת ספריות מולטימדיה בודדות או הקלת תנאי הניגון. יתר יעדי Linux שומרים על הראנרים הקיימים. המקור, התוצר, תוצאות ההשוואה וגבולותיה המדויקים מפורטים ב[הסמכת סביבת Linux WebKit](linux-webkit-runtime.md). מטריצת RC המלאה וקבלת החבילה המקורית הנפרדת עדיין נדרשות.

גרסאות המוצרים הנבדקים מתועדות בזמן הריצה. Firefox של Playwright הוא הבנייה המתוקנת שלו, לא טענה על Firefox ESR המקורי; WebKit אינו Safari. המטריצה אינה מחליפה הסמכה בטלוויזיות פיזיות או במעטפות מקוריות.

המצאי המלא כולל **35 יעדי פלטפורמה: 32 עם תמיכת HLS ושלושה יעדי Windows WebKit לממשק בלבד**. האחרונים עדיין מחייבים את שני מסלולי הטעינה/טעינה מחדש המתורגמים; בבניית WebKit שלהם אין MediaSource או HLS מקורי. זו מגבלה מוצהרת, לא כיסוי ניגון שעבר. שלושת מזהי היעד המדויקים נבדקים ב־`scripts/browser-compatibility-profile.cjs`. בדיקת יכולות חייבת לאשר את המגבלה לפני בדיקות הממשק. אם MSE (לרבות ManagedMediaSource) או HLS מקורי נעשים זמינים, השער נכשל עד לשדרוג הפרופיל. כל יעד אחר מחייב תמיכת MSE גם ב־H.264 וגם ב־AAC ואת חמשת התרחישים ללא שינוי; אובדן יכולת גורם לכישלון במקום לבחור חבילת בדיקות קטנה יותר. הבדיקה טוענת את ספריית HLS של המועמד ובוחנת את מנגנון העיבוד שבוחרת ברירת המחדל של המופע הנעול: MediaSource, אחריו ManagedMediaSource ואחריו WebKitMediaSource. האסמכתה מציינת את המנגנון ואת גרסת HLS; שינוי גרסה או ברירת מחדל מחייב סקירה מפורשת של חוזה הבדיקה.

לכן RC מלא מחייב **166 הרצות תרחישים מוצלחות** (32 × 5 + 3 × 2), עם 35 אסמכתאות יעד. קבוצת PR/לילה/beta נותרת חמישה יעדים ו־25 הרצות. כל אסמכתה מתעדת את קבוצת התרחישים המדויקת, בדיקת היכולות וכיסוי HLS שעבר או סיבת אי־תמיכה מפורשת. אלה דרישות שהוגדרו, לא טענה ש־RC מסוים כבר השלים אותן. המגבלה מאושרת ב[תצורת בניית WebKit ל־Windows](https://github.com/WebKit/WebKit/blob/56453fdfe0b0ca6258c23e6453b34f70b885d13f/Source/cmake/OptionsWin.cmake#L75) שבה משתמש Playwright 1.64 ובבדיקת סביבת הריצה הנעולה.

שני המסלולים מורידים את מזהה התוצר המדויק של המשימה המייצרת בריצה הנוכחית. לפני הגשת תיקייה שחולצה זה עתה נבדקים סכומי הביקורת של הארכיון, קומיט המקור, גיבובי bundle/provider הארוזים, סוגי הקבצים והנתיבים. בדיקות שחרור מאמתות גם את אסמכתת הבנייה הקפואה. משימות הדפדפן אינן בונות מחדש את הקוד הנבדק ומתקינות רק תלויות ייצור. שרת הבדיקות עדיין צריך את מלוא מצאי הספקים מהמקור; המהדר נטען רק כשמרכיבים bundle בפועל, לא כשקוראים את קבועי המצאי. ראיות תרחיש שנכשלו, דולגו, התיישנו או חסרות מכשילות את השער המשותף; עקבות, זהות סביבת הריצה בפועל וגיבוב המועמד נשמרים לכל יעד.

שבעת קובצי המצאי/נעילה שנוצרים מגיעים מ־`venus-os-ci-toolkit/scripts/prepare_browser_compatibility.py`. לחבילות היישום ולחבילות הדפדפנים ההיסטוריות יש קובצי נעילה נפרדים. ראנרים באירוח GitHub נשארים ברירת המחדל; התהליך המשותף שומר על בחירת גיבוי Linux שהוכנה, בעוד יעדי Windows/macOS דורשים את מערכת ההפעלה המקורית שלהם.

הכרעת השחרור המשותפת מאמתת כל יעד שנבחר ואת SHA המקור, הריצה, הניסיון, הערוץ ומזהה תוצר המועמד המדויק. RC אינו יכול להשתמש בראיות beta של חמישה יעדים. קידום ל־stable משתמש בבתי ה־RC שהתקבל. לאחר כישלון הריצו מחדש את כל תהליך ההסמכה; אסמכתאות מניסיונות ישנים אינן יכולות להשלים הסמכה חדשה.

<a id="from-source-to-accepted-candidate"></a>

## מהמקור למועמד שהתקבל

![מקור, אימות חבילה, בדיקות יכולות וראיות](diagrams/candidate-verification-flow.svg)

1. בנו את המקור שנבדק וארזו את קובצי Mode A שנוצרו. שמרו את סכום הביקורת של הארכיון ואת זהות המקור יחד עם המועמד.
2. לפני חילוץ, אמתו את הגבלת גודל הארכיון, בטיחות הנתיבים, סוגי הקבצים, המקור/גרסה ומלוא מצאי הגיבובים של הרשומות/ספקים. הסמכת שחרור בודקת גם את אסמכתת הבנייה הקפואה.
3. בדקו את גרסת הדפדפן בפועל ואת יכולות המדיה. בחרו בפרופיל המוצהר; אי־התאמה ביכולת חייבת להיכשל במקום לצמצם כיסוי בשקט.
4. הריצו את קבוצת התרחישים המדויקת מול הקבצים שחולצו, בלי בנייה מחדש. דרשו כל תרחיש בדיוק פעם אחת, ללא דילוגים, כישלונות או ניסיונות חוזרים.
5. שמרו את סביבת הריצה, היכולות, גיבוב המועמד ותוצאות התרחישים. השער המשותף בודק את היעדים הנדרשים ואת התאמת הריצה/ניסיון/מקור לפני קבלת הראיות. תיאום השחרור וקבלת המכשירים נשארים תנאים נפרדים.

<a id="what-has-been-measured-locally"></a>

## מה נמדד מקומית

![אימות שילוב מקומי: חבילות בדיקה נפרדות למכשירים ולדפדפן הארוז](diagrams/browser-verification-results.svg)

במקור `c52f4d07`, הרצת מכשיר-דפדפן Chromium המלאה עברה 196 בדיקות עם דילוג צפוי אחד על HLS מקורי. בנפרד, אותו ארכיון Mode A ארוז עבר חמישה תרחישים בכל אחד מ־Chromium 156.0.8078.4, Firefox 157.0 ו־WebKit 27.2: סך הכול 15 הצלחות, ללא דילוגים או ניסיונות חוזרים. אלו חבילות בדיקה שונות; המספרים אינם אחוז כיסוי או הוכחה שכל 35 היעדים המתארחים עברו.

[האסמכתאות השמורות](evidence/post779-local-acceptance/summary.json) מזהות את המארח בפועל כ־macOS 26.7.1. הן מבדילות אותו במפורש מתווית הפרופיל `macos-15` ואינן מסמיכות שחרור. כדי לחזור על הבדיקה המקומית ב־Mac, התקינו את התלויות הנעולות ואת דפדפני Playwright 1.64.0, בנו את המקור הנוכחי ואז הריצו את [המתכון השמור](evidence/post779-local-acceptance/reproduce.sh) עם תיקיית המאגר כארגומנט. הוא אורז את הבנייה הקיימת, בודק את המועמד ואת כל הדפדפנים ושומר אסמכתאות חדשות תחת `.compatibility/`. נדרשת פורט 4189 והוא מסרב לדרוס תיקיית `browser-candidate-web` קיימת. אל תשנו מקור בין הבנייה להפעלת המתכון. תוצאות CI מתארח ומכשירים פיזיים נעקבות בנפרד ב[דוח המימוש](implementation-report.he.md).
