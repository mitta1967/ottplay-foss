Управляемый HTML5/HLS/Shaka-плеер сохраняет одно право владения воспроизведением при восстановлении после отказа источника. Для живого канала он также может использовать до трёх явно настроенных резервных URL. Он никогда не ищет, не угадывает и не подменяет канал по его названию.

![Восстановление: одно право владения, конечные повторы, явные резервы](diagrams/stream-recovery.svg)

<a id="set-a-quality-ceiling"></a>

## Установка верхней границы качества

Откройте **Настройки → Настройки интерфейса** и задайте **Максимальную высоту видео (HLS/Shaka)** и/или **Максимальный битрейт потока (HLS/Shaka)**. Оба ограничения применяются вместе. **Автоматически** снимает соответствующее ограничение. Поддерживаются 360/480/720/1080/2160 пикселей и 1/2/4/8/16 Mbps. Настройки хранятся локально, участвуют в обычном сохранении/отмене настроек и вступают в силу при следующем запуске воспроизведения, включая перезапуск при восстановлении.

Это верхние границы, а не параметры перекодирования. Поток только 1080p не станет 720p. Если ни один заявленный вариант не подходит, плеер сообщает **No stream meets the quality limits** и прекращает повторы этого запроса. Неизвестные высота/битрейт не доказывают, что вариант HLS удовлетворяет ограничению.

Варианты HLS фильтруются до загрузки фрагментов. Текущий hls.js удаляет неподходящие варианты; старые сборки без `removeLevel` могут сохранять лишь безопасный непрерывный префикс и иногда отклоняют манифест, в котором подходящие варианты находятся дальше. Shaka использует ограничения приложения `maxHeight`/`maxBandwidth`. Автоматическая адаптация продолжается среди оставшихся вариантов.

Эти настройки действуют для управляемых движков HLS и Shaka. Обычный HTML5, нативные декодеры платформ и сохранённые движки TV/STB не предоставляют тех же средств управления. Режим Auto может выбрать нативное воспроизведение; настройка не принуждает его к MSE. Плеер не переведёт уже ограниченный HLS-запрос на неограниченное нативное воспроизведение лишь ради обхода ошибки декодирования. Нативный транскодер, автоматический аппаратный тест производительности или утверждение о физическом выводе 720p здесь не подразумеваются.

<a id="configure-explicit-backups"></a>

## Настройка явных резервов

1. Запустите нужный канал прямого эфира.
2. Откройте **Информация → Резервные потоки**.
3. Выберите позицию 1, 2 или 3 и введите полный HTTP/HTTPS URL медиа.
4. Повторно откройте занятую позицию для **Редактировать** или **Удалить**. Заново запустите канал, чтобы использовать обновлённый список.

Каждая позиция принадлежит текущему пространству хранения провайдера и точной паре `sourceId`/`channelId`. Текущее поколение воспроизведения и конфигурация источника ограничивают действие редактора. Смена источника при открытом диалоге не позволяет этому диалогу сохранить данные в новый источник. Одновременное изменение той же позиции отклоняется, а не перезаписывается.

Первый URL остаётся обычным источником канала. Дублирующиеся и пустые позиции пропускаются. Допускается максимум 256 записей каналов и 256 KiB конфигурации. URL с учётными данными в user-info, пробельными или управляющими символами, обратными косыми чертами или некорректным портом отклоняются. Токены провайдера в query-параметрах всё же могут входить в URL медиа: резервные настройки — локальная конфигурация источника, а не механизм обмена учётными данными или их публикации.

Резервы действуют **только в прямом эфире**. Архивные и VOD-запросы никогда не используют живую альтернативу: запись, начало отсчёта времени, права и семантика перемотки могут отличаться. Владелец должен предоставить эквивалентные разрешённые живые адреса. Совпадение названия канала не доказывает эквивалентность. Сохранённый идентификатор канала, избранное и привязка EPG не меняются при замене транспортного адреса.

<a id="recovery-guarantees"></a>

## Гарантии восстановления

- У запроса есть максимум **две отложенные временные повторные попытки того же URL суммарно** и по одному переходу вперёд к каждому из трёх резервов: не более пяти пересозданий после первоначального запуска. Новый экземпляр декодера или успешно полученный манифест не сбрасывают бюджет. Существующее ограниченное восстановление сети и декодирования внутри HLS выполняется до этой внешней политики.
- Ошибки разбора манифеста/уровня HLS допускают максимум одно переподключение к тому же URL на запрос в рамках общего лимита двух повторов. Новый декодер или резервный адрес этот предел не сбрасывают.
- Сетевые ошибки без статуса, HTTP 408/429 и 5xx могут использовать временный бюджет. Другие HTTP 4xx могут перейти к настроенной альтернативе, но не повторяют тот же URL. **HTTP 401/403 и ошибки входа в источник завершают запрос**, без проб альтернативных учётных данных или резервных адресов.
- Ошибки декодирования могут переходить вперёд к явному резерву. Невыполнимые ограничения качества завершают запрос. Циклического возврата к основному источнику нет.
- Задержка составляет 500 ms, 1 s, 1.5 s, затем максимум 2 s. Повторные обратные вызовы объединяются.
- Pause удаляет запланированный таймер, сохраняя ожидающую повторную попытку; Resume планирует его заново. Stop, режим ожидания, замена источника и канала делают отложенные обратные вызовы недействительными. После окончательного отказа нужен явный повторный выбор, а не автоматический запуск выведенного из работы декодера.
- Ошибки загрузки Shaka и критические события ошибок используют этот же путь; ошибки отмены игнорируются. Повторное подключение ждёт асинхронного уничтожения Shaka.
- При восстановлении заново разрешается непрозрачная ссылка Stalker и повторно готовится доступ к защищённому источнику. Просроченный iOS loopback URL не используется повторно. Позиция VOD/архива снимается до разборки; живые резервы стартуют на своей текущей точке эфира.

Эта политика не добавляет второго наблюдателя за остановившимися кадрами. Существующее восстановление kiosk, Auto/native и HLS продолжает покрывать свои наблюдаемые отказы. Молча зависший поток, о котором ни один существующий детектор не сообщил ошибку, требует отдельной диагностики.

<a id="verification-and-observability"></a>

## Проверка и наблюдаемость

`window.__ottStreamPolicy.snapshot()` показывает имя движка, запрошенные ограничения, возможности/доступность, число повторов, индекс адреса и состояние восстановления. Он не содержит URL потока или учётных данных провайдера. Индекс ноль означает обычный источник; следующие индексы относятся к непустым уникальным альтернативам. Это диагностическое состояние, а не стабильный API дистанционного управления.

Выполните:

```sh
node tests/test_stream_policy.cjs
node tests/test_port_engine_lifecycle.cjs
node tests/test_settings_parity.cjs
node tests/test_media_backend.cjs
npm run test:localization
npm run typecheck
npm run build:server
node scripts/check-es5.cjs --server-only
```

Тесты проверяют фильтрацию качества при немонотонном порядке вариантов, недоступные метаданные, редактирование в области источника, конфликты позиций, повторные ошибки, ограниченные бюджеты, ошибки HTTP-авторизации, отмену паузой/остановкой/сменой источника, разборку Shaka и сохранение позиции VOD. Пять новых подписей воспроизведения переведены во всех 88 поставляемых языковых пакетах; автоматическая проверка соответствия не является редактурой носителем языка. Физическое воспроизведение на TV/D1 и манифесты конкретных провайдеров всё ещё требуют проверки на устройстве. [Редактируемый исходник диаграммы](diagrams/stream-recovery.mmd).
