การตรวจอุปกรณ์ สื่อ ES5/worker รุ่นเก่า UI แบบเนทีฟ และ HLS แบบเนทีฟของ Apple ที่มีอยู่ยังเป็นข้อบังคับ เวิร์กโฟลว์ TypeScript ที่ใช้ร่วมกันยังรันสถานการณ์ Plex กับไฟล์เก็บถาวร Mode A ที่แพ็กไว้ตรงชุดนั้น ได้แก่ขั้นตอนโหลด/โหลดซ้ำที่แปลภาษาแล้วสองแบบ การคงอัตราส่วนภาพของ HLS.js และ Video.js เมื่อเปลี่ยนสื่อหรือโหลดซ้ำ และการจบตอนตามธรรมชาติในโหมดคีออสก์เข้มงวดด้วย HLS.js สถานการณ์สื่อใช้การถอดรหัสจริง ทุกสถานการณ์ใช้ DOM และอินพุตจริง มีเพียงข้อมูล Plex และแหล่งสื่อเท่านั้นที่เป็นข้อมูลทดสอบสังเคราะห์ในเครื่อง

ชุดข้อมูลทดสอบอัตราส่วนภาพรีมัลติเพล็กซ์ทรานสปอร์ตสตรีม H.264/AAC ที่เก็บในรีโพซิทอรีเป็น fMP4 แยกกัน ส่วนหัวเริ่มต้นใช้แบรนด์ `iso6` และระยะเวลาภาพยนตร์/แทร็กเป็นศูนย์ ตาม [RFC 8216 ส่วน 3.3](https://www.rfc-editor.org/rfc/rfc8216#section-3.3) รายการตัวอย่าง AVC ยังใช้บิตสงวนที่จำเป็นในจำนวน SPS และค่าคงที่แบบมีเครื่องหมาย `-1` ในฟิลด์ท้าย `pre_defined` สิ่งนี้แก้ไวยากรณ์คอนเทนเนอร์จากมัลติเพล็กเซอร์ทดสอบเวอร์ชันที่ตรึงไว้ สัญญาของชุดข้อมูลตรวจส่วนหัว ปฏิเสธกล่องที่ผิดรูปแบบ และยืนยันว่าชุดพารามิเตอร์โคเดก ID แทร็ก สเกลเวลา และไบต์ของส่วนสื่อไม่เปลี่ยน เป็นการตรวจอินพุตสังเคราะห์เท่านั้น ไม่ได้พิสูจน์การเล่นในเบราว์เซอร์ด้วยตัวเองหรือแทนเมทริกซ์ RC เต็มชุด

Pull request ต้องใช้ Chromium, Firefox และ WebKit รุ่นปัจจุบันบน Linux, Chromium บน Windows และ WebKit บน macOS บิลด์ nightly และ beta ต้องผ่านห้าเป้าหมายนี้เช่นกัน การรับรอง RC ต้องครบทั้ง 35 เป้าหมายที่ประกาศ: Playwright/เบราว์เซอร์สามรุ่นที่ระบุแน่นอนบน Linux, Windows และ macOS พร้อม Chrome/Edge รุ่นเสถียรที่ติดตั้งในทั้งสามระบบ และ Chrome/Edge beta บน Linux เป้าหมาย macOS WebKit รุ่นเก่าสองชุด (Playwright 1.62.1 และ 1.63.0) ใช้ `macos-15-intel` หลักฐานบันทึกสถาปัตยกรรมโปรเซสจริงและปฏิเสธรันเนอร์ ARM การวินิจฉัย MSE โดยตรงพบว่าไบต์เริ่มต้น H.264 และสื่อชุดเดียวกันทำงานจบบน Intel กับ 1.63 และ ARM กับ 1.64 แต่ WebKit เก่าใน VM macOS 15 ARM ค้างก่อน `updateend` การเปลี่ยนคอนเทนเนอร์ ใช้ ManagedMediaSource หรือเปิดหน้าต่างเบราว์เซอร์ไม่ได้แก้ปัญหา สองเป้าหมายนี้ยังต้องผ่านสถานการณ์เล่น/UI เดิมทั้งห้า การเลือกรันเนอร์นี้ไม่ใช่ข้อสรุปสำหรับอุปกรณ์ macOS จริงทุกเครื่องหรือ Safari แบบเนทีฟ เมื่อสร้างรายการใหม่ต้องรักษาค่าทับรันเนอร์ที่ตรวจทานแล้ว สัญญาโปรไฟล์จะปฏิเสธการลบค่าเหล่านี้

Linux WebKit ทั้งสามรุ่นใช้รันเนอร์ x64 `ubuntu-26.04` อย่างชัดเจน การเปรียบเทียบรันไทม์ทางการที่ตรวจทานแล้วทำซ้ำความล้มเหลวในการเปลี่ยนสถานะคีออสก์เข้มงวดบน Ubuntu 24.04 ได้ ขณะที่ตัวเลือกเผยแพร่เดียวกันกับห้าสถานการณ์ที่ไม่แก้ไขผ่านสี่ครั้งติดต่อกันบน Ubuntu 26.04 จึงเป็นการเลือกรันไทม์ที่สอดคล้องและรองรับ โดยไม่เปลี่ยนไลบรารีมัลติมีเดียรายตัวหรือผ่อนปรนเงื่อนไขการเล่น เป้าหมาย Linux อื่นยังใช้รันเนอร์เดิม ดูซอร์ส อาร์ติแฟกต์ ผลเปรียบเทียบ และข้อจำกัดที่แน่นอนใน [การรับรองรันไทม์ Linux WebKit](linux-webkit-runtime.md) เมทริกซ์ RC เต็มชุดและการตรวจรับแพ็กเกจเนทีฟแยกต่างหากยังจำเป็น

เวอร์ชันผลิตภัณฑ์ที่ทดสอบถูกบันทึกขณะรัน Playwright Firefox เป็นบิลด์ที่แก้แพตช์ของโครงการนั้น ไม่ใช่หลักฐานของ Firefox ESR แบบเนทีฟ และ WebKit ไม่ใช่ Safari เมทริกซ์นี้ไม่แทนการรับรองบนทีวีจริงหรือเชลล์เนทีฟ

รายการทั้งหมดมี **35 เป้าหมายแพลตฟอร์ม: 32 เป้าหมายรองรับ HLS และ Windows WebKit สามเป้าหมายสำหรับ UI เท่านั้น** กลุ่มหลังยังต้องผ่านขั้นตอนโหลด/โหลดซ้ำที่แปลภาษาแล้วทั้งสองแบบ บิลด์ WebKit ของกลุ่มนี้ไม่มี MediaSource หรือ HLS แบบเนทีฟ นี่คือข้อจำกัดที่ประกาศไว้ ไม่ใช่ความครอบคลุมการเล่นที่ผ่านแล้ว ID สามเป้าหมายที่แน่นอนผ่านการตรวจทานใน `scripts/browser-compatibility-profile.cjs` ตัวตรวจความสามารถต้องยืนยันข้อจำกัดก่อนรันทดสอบ UI หาก MSE (รวม ManagedMediaSource) หรือ HLS แบบเนทีฟพร้อมใช้ เกตจะต้องล้มเหลวจนกว่าจะปรับโปรไฟล์ ทุกเป้าหมายอื่นต้องรองรับ MSE ทั้ง H.264 และ AAC และผ่านห้าสถานการณ์เดิม การสูญเสียความสามารถทำให้ล้มเหลว ไม่ใช่เลือกชุดทดสอบที่เล็กลง ตัวตรวจโหลดไลบรารี HLS ของตัวเลือกเผยแพร่และตรวจแบ็กเอนด์ที่ค่าเริ่มต้นของอินสแตนซ์ตรึงเวอร์ชันเลือก: MediaSource ตามด้วย ManagedMediaSource แล้ว WebKitMediaSource หลักฐานระบุแบ็กเอนด์และเวอร์ชัน HLS การเปลี่ยนค่าเริ่มต้นหรือเวอร์ชันต้องตรวจทานสัญญาของตัวตรวจอย่างชัดเจน

ดังนั้น RC เต็มชุดต้องมี **การรันสถานการณ์สำเร็จ 166 ครั้ง** (32 × 5 + 3 × 2) พร้อมหลักฐานเป้าหมาย 35 ชุด ส่วนย่อย PR/nightly/beta ยังคงห้าเป้าหมายและ 25 ครั้ง แต่ละหลักฐานบันทึกชุดสถานการณ์ที่แน่นอน การตรวจความสามารถ และ HLS ที่ผ่านหรือเหตุผลไม่รองรับอย่างชัดเจน ตัวเลขเหล่านี้คือข้อกำหนดที่ตั้งไว้ ไม่ใช่คำกล่าวว่า RC ใดทำครบแล้ว ข้อจำกัดยืนยันโดย [การกำหนดค่าบิลด์ WebKit Windows](https://github.com/WebKit/WebKit/blob/56453fdfe0b0ca6258c23e6453b34f70b885d13f/Source/cmake/OptionsWin.cmake#L75) ที่ Playwright 1.64 ใช้และตัวตรวจรันไทม์ที่ตรึงไว้

ทั้งสองเส้นทางดาวน์โหลด ID อาร์ติแฟกต์ที่แน่นอนจากงานผู้สร้างในรันปัจจุบัน ก่อนให้บริการไดเรกทอรีที่แตกใหม่ จะตรวจเช็กซัมไฟล์เก็บถาวร คอมมิตต้นทาง แฮช bundle/provider ในแพ็กเกจ ชนิดไฟล์ และพาธ การตรวจรีลีสยังยืนยันหลักฐานบิลด์ที่ตรึงไว้ งานเบราว์เซอร์ไม่สร้างโค้ดที่ทดสอบใหม่และติดตั้งเฉพาะดีเพนเดนซี production เซิร์ฟเวอร์ทดสอบยังต้องใช้รายการ provider ครบจากซอร์ส คอมไพเลอร์โหลดเฉพาะเมื่อประกอบ bundle จริง ไม่ใช่เมื่ออ่านค่าคงที่รายการ หลักฐานสถานการณ์ที่ล้มเหลว ข้าม เก่า หรือขาดหายทำให้เกตร่วมล้มเหลว โดยเก็บ trace ตัวตนรันไทม์จริง และไดเจสต์ตัวเลือกเผยแพร่สำหรับทุกเป้าหมาย

ไฟล์รายการ/lock ที่สร้างขึ้นเจ็ดไฟล์มาจาก `venus-os-ci-toolkit/scripts/prepare_browser_compatibility.py` แพ็กเกจแอปและแพ็กเกจเบราว์เซอร์ย้อนหลังมี lockfile แยกกัน รันเนอร์ GitHub-hosted ยังคงเป็นค่าเริ่มต้น เวิร์กโฟลว์ร่วมคงตัวเลือกสำรอง Linux ที่เตรียมไว้ ส่วน Windows/macOS ต้องใช้ OS เนทีฟของตน

คำตัดสินรีลีสร่วมตรวจทุกเป้าหมายที่เลือกและ SHA ซอร์ส รัน ครั้งที่ลอง ช่องทาง และ ID อาร์ติแฟกต์ตัวเลือกเผยแพร่ที่แน่นอน RC ใช้หลักฐาน beta ห้าเป้าหมายไม่ได้ การเลื่อนเป็น stable ใช้ไบต์ของ RC ที่รับแล้ว หลังล้มเหลวให้รันเวิร์กโฟลว์รับรองทั้งหมดใหม่ หลักฐานจากครั้งเก่าไม่สามารถทำให้การรับรองใหม่เสร็จสมบูรณ์

<a id="from-source-to-accepted-candidate"></a>

## จากซอร์สสู่ตัวเลือกเผยแพร่ที่ผ่านการรับรอง

![ซอร์ส การตรวจแพ็กเกจ ความสามารถ และหลักฐาน](diagrams/candidate-verification-flow.svg)

1. สร้างจากซอร์สที่ตรวจทานแล้วและแพ็กไฟล์ Mode A ที่ได้ เก็บเช็กซัมไฟล์เก็บถาวรและตัวตนซอร์สไว้กับตัวเลือกเผยแพร่
2. ก่อนแตกไฟล์ ตรวจขีดจำกัดขนาดไฟล์เก็บถาวร พาธที่ปลอดภัย ชนิดไฟล์ ซอร์ส/เวอร์ชัน และรายการแฮช entry/provider ทั้งหมด การรับรองรีลีสยังตรวจหลักฐานบิลด์ที่ตรึงไว้
3. ตรวจเวอร์ชันเบราว์เซอร์จริงและความสามารถสื่อ เลือกโปรไฟล์ที่ประกาศ หากความสามารถไม่ตรงต้องล้มเหลวแทนการลดความครอบคลุมเงียบ ๆ
4. รันชุดสถานการณ์ที่แน่นอนกับไฟล์ที่แตกแล้วโดยไม่สร้างใหม่ ทุกสถานการณ์ต้องรันครั้งเดียว ไม่มีการข้าม ล้มเหลว หรือลองซ้ำ
5. เก็บรันไทม์ ความสามารถ ไดเจสต์ตัวเลือกเผยแพร่ และผลสถานการณ์ เกตร่วมตรวจเป้าหมายที่จำเป็นและรัน/ครั้งที่ลอง/ซอร์สที่ตรงกันก่อนรับหลักฐาน การประสานงานรีลีสและการตรวจรับอุปกรณ์ยังเป็นเงื่อนไขแยกกัน

## สิ่งที่วัดในเครื่องแล้ว

ที่ซอร์ส `c52f4d07` การรันชุดอุปกรณ์-เบราว์เซอร์ Chromium เต็มชุดผ่าน 196 การทดสอบและข้าม HLS เนทีฟหนึ่งรายการตามคาด แยกต่างหาก ไฟล์เก็บถาวร Mode A ชุดเดียวกันผ่านห้าสถานการณ์ในแต่ละ Chromium 156.0.8078.4, Firefox 157.0 และ WebKit 27.2 รวมผ่าน 15 รายการ ไม่มีข้ามหรือลองซ้ำ ชุดเหล่านี้ต่างกัน จำนวนไม่ใช่เปอร์เซ็นต์ความครอบคลุมหรือหลักฐานว่าเป้าหมาย hosted ทั้ง 35 ผ่านแล้ว

[หลักฐานที่บันทึก](evidence/post779-local-acceptance/summary.json) ระบุโฮสต์จริง macOS 26.7.1 โดยแยกจากป้ายโปรไฟล์ `macos-15` อย่างชัดเจน และไม่ได้รับรองรีลีส หากต้องการทำซ้ำบน Mac ให้ติดตั้งดีเพนเดนซีที่ล็อกและเบราว์เซอร์ Playwright 1.64.0 สร้างซอร์สปัจจุบัน แล้วรัน [ขั้นตอนที่บันทึก](evidence/post779-local-acceptance/reproduce.sh) โดยส่งไดเรกทอรีรีโพซิทอรีเป็นอาร์กิวเมนต์ ขั้นตอนนี้แพ็กบิลด์ที่มี ตรวจตัวเลือกเผยแพร่ ตรวจทุกเบราว์เซอร์ และบันทึกหลักฐานใหม่ใต้ `.compatibility/` ต้องใช้พอร์ต 4189 และจะปฏิเสธการเขียนทับไดเรกทอรี `browser-candidate-web` ที่มีอยู่ อย่าเปลี่ยนซอร์สระหว่างสร้างกับรันขั้นตอน ผล CI hosted และอุปกรณ์จริงติดตามแยกใน [รายงานการพัฒนา](implementation-report.th.md)
